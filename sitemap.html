Product Architecture — Two Models Compared

Not a redesign. A side-by-side map of what each area of the product owns, why it exists, and how people move between them — current architecture next to the model stakeholders have proposed, in the same structure so they can be read against each other line by line.

Before changing the interface, we need to agree on the product architecture: what each area owns, why it exists, and how users move between them.

The goal of these maps is not to choose a UI. It is to agree on the product model first.

Version A

Current Architecture

See it live ↗

Chat and Agents are treated as distinct product areas.

1

Chat

Purpose
The main interaction point with Starchild.
Primary user goal
Ask questions, request help, execute tasks, start workflows, and interact with the system without needing to choose a specialized agent first.
Core content
  • Conversation
  • Input / composer
  • AI responses
  • Current activity / status
  • Action UI when needed
Core actions
  • Send messages, ask questions
  • Execute simple tasks
  • Create simple ongoing tasks
  • Delegate to an existing agent
  • Navigate to other product areas
  • Start a new chat
System behavior
Acts as the general intelligence / orchestrator. Understands intent, responds directly, creates simple ongoing tasks, and can route work to specialized agents when relevant.
Relationships / navigation
The point everything else is reached from: Chat routes into a specific Agent's own thread when work is delegated — a route that never leads back into one shared conversation.
Why this needs to exist as a separate area
It is the universal entry point and should work even if the user never creates a specialized agent.
Owns
General conversation Intent understanding Simple actions Orchestration Ongoing-task creation Delegation
2

Agents

Purpose
Create and use specialized persistent agents with their own role, rules, tools, and history.
Primary user goal
Have a dedicated agent for a specific domain, mission, workflow, or context.
Core content
  • Agent list
  • Individual agent conversation
  • Name / identity, mission, rules
  • Tools / connectors, history
  • Controls
Core actions
  • Create agent, configure agent
  • Chat directly
  • Edit rules, connect tools
  • Pause / delete / manage
System behavior
Each agent maintains its own persistent context, specialized mission, rules, connectors, and history.
Relationships / navigation
Reached from the Agents list, separate from Chat's own thread — creating or opening an Agent never touches Chat's own history, and each Agent's thread is self-contained.
Why this needs to exist as a separate area
An agent is not only a task. It is a persistent specialized intelligence with its own operating context.
Owns
Specialized mission Persistent context Dedicated rules Connectors / tools Dedicated history Independent controls

Version B

Proposed / Stakeholder Architecture

Reflects the concern that “New Chat” and “New Agent” may be competing concepts.

Core stakeholder feedback: — Multiple agents can exist, but they are optional. One agent may be enough for many users. — The purpose of “New Chat” is unclear; “New Chat” + “New Agent” can feel like two different ways to create a separate context. — The product may need to choose one primary philosophy rather than giving equal weight to both. — Users still need a clear place to see what routines / Jobs are currently running.
1

Main Agent / Chat

Purpose
Be the user's primary, continuous relationship with Starchild.
Primary user goal
Talk, ask for help, delegate tasks, create routines, and manage work from one ongoing context.
Core content
  • Persistent conversation
  • Current tasks / actions
  • System responses
  • Contextual status
  • Access to ongoing work
Core actions
  • Send messages, ask questions
  • Create routines / Jobs
  • Perform tasks, delegate
  • Optionally create an additional agent when needed
System behavior
Acts as the primary persistent intelligence. The user does not need to create multiple chats to separate conversations unless there is a very clear reason.
Relationships / navigation
The default landing point. Creates Routines/Jobs and, when justified, an Extra Agent — both without leaving the Main Agent's own continuous thread.
Why this needs to exist as a separate area
This is the default relationship between user and Starchild.
Owns
Primary conversation Accumulated context Simple tasks Creation of routines Delegation Creation of additional agents when genuinely needed
2

Routines / Jobs

Purpose
Show all ongoing, recurring, or continuously monitored work.
Primary user goal
Understand what is running, when it runs, current status, and whether attention is required.
Core content
  • Routine / Job title
  • Trigger / schedule
  • Current state, latest result
  • Active / paused
  • Alerts / exceptions
Core actions
  • Edit
  • Pause / resume
  • Cancel
  • Inspect
System behavior
Jobs continue running independently from the active conversation.
Relationships / navigation
Created from the Main Agent. A status view, not a conversation — the user checks in, they don't chat with a Job.
Why this needs to exist as a separate area
Users need one clear place to see “what is currently running.”
Owns
Recurring work Monitoring Scheduled tasks Alerts Status Ongoing execution
3

Additional Agents — Optional

Purpose
Create a separate agent only when the user genuinely needs a specialized persistent context.
Primary user goal
Separate a domain, mission, set of tools, rules, or history from the Main Agent.
Core content
Examples: Research Agent, Trading Agent, Inbox Manager, Project Agent.
Core rule
The user does not need multiple agents by default. One Main Agent can be enough.
System behavior
Each Extra Agent maintains its own specialized context, mission, tools, and rules — same behavior as Version A's Agents, scoped down to only when justified.
Relationships / navigation
Reached from the Main Agent when a specialized context is created. Each Extra Agent keeps its own thread, separate from the Main Agent's.
Why this needs to exist as a separate area
A new agent should exist only when there is a strong structural reason for independent context, mission, tools, rules, history, and controls.
Owns
Specialized persistent context Specialized mission Dedicated tools / connectors Independent rules and history

A vs B — Side by Side

The same ten questions, answered once from each model, so a gap between them is visible on the row rather than buried in two separate documents.

Question Version A Version B
What is Chat? General orchestrator / main entry point. Primary persistent Main Agent.
What is an Agent? A specialized persistent entity alongside Chat. An optional specialized extension of the Main Agent.
Can users create multiple Agents? Yes, as a normal product structure. Yes, but only when genuinely useful.
What is the purpose of New Chat? Start a separate conversation / context. Low value / unclear / possibly unnecessary.
What creates a new context? Both New Chat and New Agent can separate context. Mainly a new Agent, when specialization is needed.
Where does ongoing work live? Not a dedicated area — Chat creates it, but there's no separate place to see it running. Jobs / Routines.
Where does history live? Chat history + per-Agent history. Main Agent history + optional per-Agent history.
Who delegates work? Chat / Chief Agent. Main Agent.
Why create another Agent? To create a specialized persistent intelligence. Only when mission, tools, rules, or context need to be isolated.
Main tradeoff More flexibility, but potentially more conceptual complexity. Simpler mental model, but less emphasis on multiple parallel contexts.

Decisions the Team Needs to Make

These maps don't answer these questions — they only make the questions visible. Nothing here should be resolved by default or by whoever builds the next screen first.

  1. What creates a new context in Starchild: a new chat, a new agent, or both?
  2. If one Main Agent can handle most of the user's work, what specific condition justifies creating another agent?
  3. What is the unique purpose of “New Chat”?
  4. Where does ongoing work live, and how does the user see what is currently running?
  5. Are Jobs / Automations a feature of the Main Agent, or a standalone product area?
  6. Where should connectors and tools be configured: globally, per Main Agent, or per specialized Agent?
  7. What should be persistent: conversation history, agent memory, task history, or all of them?
  8. Which architecture creates the clearest user mental model with the least duplication?
Scope of this document: product model only — what each area owns, why it exists, and how people move between them. Neither version is presented as the recommended one; both are represented neutrally so the team can compare and agree on the architecture before any further interface work.
